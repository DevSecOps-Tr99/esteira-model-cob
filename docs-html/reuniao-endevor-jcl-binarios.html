Alinhamento com a esteira Endevor real e o risco dos binários/hexadecimais

Registro da reunião "Reunião alinhamento JCL banco" de 31/08/2026 (Ana Exemplo, Bruno Exemplo, Carlos Exemplo) — primeiro contato com quem já opera uma esteira real de migração do Endevor no banco. Objetivo deste documento: 1) traçar o paralelo entre o que a Ana descreveu e o que esteira-model-cob propõe hoje, e 2) registrar o ponto de atenção mais importante que ela levantou — componentes com caracteres hexadecimais não roundtrippable, que só podem trafegar como binário — e o plano de ação para tratar isso aqui.

1. O paralelo: a esteira que a Ana já opera

O time dela migra uma esteira Endevor (escopo maior que o nosso: COBOL, Assembler, mapas BMS, Control-M e JCL) para um pipeline com ferramental oficial da IBM. Fluxo descrito na reunião:

Analista altera componente (baixa do Git para o mainframe)
        ↓
Z Builder                  ← "nasce" aqui; builda o componente e marca o deployType
        ↓
DBB (Dependency Based Build) ← empacota os artefatos gerados
        ↓
JFrog Artifactory           ← repositório dos pacotes
        ↓
Wazi Deploy ("AZ/OZ Deploy")← consulta o deployType, decide biblioteca-alvo por
                               ambiente, executa jobs de validação antes/depois
        ↓
Biblioteca-alvo no mainframe (ex.: HBBR.PR1.DECKLIB para JCL, .PROCLIB, .PARMLIB…)

A configuração real que ela mostrou (reusable-configurations/mainframe/instances/cwb/dbb/) tem um Transfer.yaml por tipo de componente (copyJCL → copyMode: TEXT, deployType: JCL; copyZCFG → deployType: CONFIG; etc.) e um info.toml que mapeia deployType → dataset-alvo por ambiente ([cwbp.deploy.lib.jcl] target = "HBBR.PR1.DECKLIB", lib.dbrmb/lib.dbrmo já vêm com spec = "binary", lib.debugb/o com spec = "debug"). Conexão com o mainframe: Zowe ("Ozzy"/RC API), que ela descreveu como a porta de entrada — não necessariamente amarrada ao DBB/Wazi Deploy.

2. O ponto de atenção: hexadecimais "hard-coded" e caracteres não roundtrippable

Achado dela na migração do Endevor (instância CWB): existem componentes — JCL, copybooks (COPY) e PROC — em que alguém, no terminal 3270/ISPF, ligou o modo hex do editor (HEX ON) e digitou um valor hexadecimal diretamente dentro do componente, no lugar de, por exemplo, escrever VALUE X'...' em COBOL. O resultado visual no editor é um espaço em branco, mas o byte gravado ali não tem correspondência em ASCII/UTF-8.

Consequência prática, nas palavras dela: qualquer transporte desses componentes que não seja binário corrompe o conteúdo — ela testou baixar via zFS/USS, via Zowe e via RSE API, e as três formas corromperam o dado. Isso vale tanto para os componentes de aplicação (JCL/COPY/PROC) quanto para os componentes de Control-M, pelo mesmo motivo.

Contingência que o time dela adotou (ainda sem solução definitiva — depende de uma refatoração futura do código-fonte para eliminar esses hexadecimais hard-coded):

  1. O desenvolvedor altera o componente diretamente no mainframe.
  2. Baixa o componente como binário (não como texto).
  3. Inclui esse binário na branch e trafega normalmente pelo Git.
  4. No deploy, o binário é restabelecido para EBCDIC para o componente voltar a ser executável/legível no mainframe.

Recomendação dela para não sermos surpreendidos: fazer uma busca hexadecimal (hex search) nas bibliotecas reais que vão entrar no escopo, via ISPF/3270, procurando por esses caracteres antes de migrar qualquer componente — foi assim que o time dela encontrou o problema na instância CWB.

Decisão fechada em 31/08/2026: diferente do time da Ana (que trata isso como contingência temporária até uma refatoração futura do código-fonte), em esteira-model-cob o tratamento binário é adotado como parte definitiva do desenho — não como stopgap. O guard de binário, o .gitattributes e o caminho de deploy em modo binary (seção 4) não são descartados quando/se a refatoração acontecer; continuam sendo a forma permanente de tratar qualquer componente hex-declarado que apareça no escopo.

A tabela de bytes (desafios-binarios.txt)

O arquivo que ela indicou como referência (desafios-binarios.txt, na raiz de C:\Projetos\cliente\) lista os pontos de código problemáticos, em duas classes:

  • Non-roundtrippable: 0D, 0E, 0F, 15, 25
  • Non-printable: 00–0C, 10–14, 16–24, 26–3F

Isto é essencial a faixa de controle (C0) do code page EBCDIC usado no mainframe (tipicamente IBM-037/1047) — bytes que, ao serem tratados como texto e convertidos para ASCII/UTF-8 (ou vice-versa), não têm mapeamento seguro de ida-e-volta. Qualquer pipeline que abra esses arquivos em modo texto (decode/encode, normalização de fim de linha do Git, etc.) já corrompe o dado — não é um problema de ferramenta específica, é inerente ao byte em si.

3. Gap identificado em esteira-model-cob hoje

  1. Todo o motor lê os componentes como texto. parser.py e o restante do pipeline assumem .read_text()/UTF-8. Nunca foi desenhado (nem testado) para bytes fora do intervalo seguro de texto.
  2. Não existe .gitattributes. Sem ele, o Git pode normalizar fim de linha e tratar como texto qualquer arquivo — risco real de corromper um componente binário assim que ele entrar no repositório.
  3. Falta uma camada de "gravar o fonte na biblioteca-alvo". Hoje ExecutionAdapter/ZosmfAdapter (Fase 2, docs/integracao-zos.md) cobre só a submissão e o acompanhamento do job (z/OSMF Jobs REST API). Não existe nada equivalente ao papel do Wazi Deploy: decidir a biblioteca-alvo por ambiente e gravar o JCL/COPY/PROC lá — inclusive em modo binário quando necessário. São duas responsabilidades distintas até na própria z/OSMF (restjobs/jobs vs. restfiles/ds), e hoje só a primeira está desenhada.
  4. Não existe detecção de componentes "hex-declarados". Nenhum gate verifica, byte a byte, se um componente contém os valores listados em desafios-binarios.txt antes de decidir tratá-lo como texto.
  5. Não existe um equivalente ao deployType/Transfer.yaml dela. Nosso config/ não tem hoje uma classificação de artefato → biblioteca-alvo por ambiente (mesmo que bem mais simples, já que nosso escopo é só JCL).

4. Plano de ação

Curto prazo — dentro do escopo atual da POC (sem depender de acesso real)

  1. Guarda de binário no pipeline. Novo módulo (binary_guard.py ou verificação em rules_engine.py) que lê cada componente em modo binário e verifica a presença dos bytes de desafios-binarios.txt antes de qualquer decodificação para texto. Se detectado, o componente é marcado requires_binary_transfer e vira um finding no Quality Gate (hoje o pipeline nem chegaria a rodar sem quebrar, se um desses componentes entrasse como texto). Tratamento definitivo (ver decisão na seção 2), não um workaround a remover depois. → Implementado: esteira_model_cob/binary_guard.py + comando binary-guard (esteira_model_cob/cli.py). Contrato importante descoberto ao implementar: os valores da tabela só fazem sentido sobre bytes EBCDIC crus — os mesmos números (0x00-0x3F) são dígitos e pontuação comuns em ASCII/UTF-8, então o guard não roda sobre o JCL versionado em jcl/ (isso seria falso positivo); ele é um comando/caminho separado, para bytes ainda não convertidos vindos do mainframe. Ver docstring do módulo.
  2. .gitattributes. Definir JCL/COPY/PROC como texto por padrão, com instrução documentada de como marcar um componente específico como binário (-text -diff) quando o guard do item 1 o sinalizar — até termos automação completa disso. → Implementado: .gitattributes na raiz do repositório.
  3. Massa de teste com hex embutido. Como nenhum JCL/PROC real do nosso escopo tem hoje esse tipo de caractere, criar 1–2 fixtures sintéticos cobrindo o caso non-roundtrippable e o caso non-printable (gerados via script, não digitados à mão — para garantir os bytes exatos). É o que valida de ponta a ponta o guard do item 1, o .gitattributes do item 2 e o caminho de deploy binário do item 5, sem depender de acesso real ao mainframe. → Implementado, com um ajuste em relação ao plano original: as fixtures não ficam em jcl//proc/ como texto ASCII com bytes embutidos — pelo motivo explicado no item 1 (os mesmos valores numéricos são inofensivos em ASCII), elas precisam ser bytes EBCDIC genuínos. scripts/gen_test_fixtures.py codifica um trecho de copybook em cp037 e grava duas versões em tests/fixtures/: uma limpa (copybook_ebcdic_limpo.bin) e uma com 2 bytes de controle inseridos (copybook_ebcdic_hex_declarado.bin) — cobertas por tests/test_binary_guard.py.
  4. Modelar a segunda API do z/OSMF. Atualizar docs/integracao-zos.md com a distinção Jobs REST API (execução, já documentada) vs. Files REST API (PUT /zosmf/restfiles/ds/..., parâmetro de encoding binary) ou zowe zos-files upload file-to-data-set --binary — caminho confirmado (seção 1): Zowe/z/OSMF + Python direto, sem DBB/Wazi Deploy. → Documentado (seção "Gravação do fonte..." em integracao-zos.md); implementação de código só na Fase 2, quando houver acesso real ao mainframe (item 9b).
  5. Classificação de artefato → biblioteca-alvo. Adicionar ao config/ um equivalente enxuto do deployType/Transfer.yaml/info.toml da Ana (nosso escopo é só JCL, então bem mais simples): mapear ambiente (TU/TI/PRD) → dataset-alvo, e permitir marcar copyMode: binary por componente. → Implementado: config/deploy_targets.yml + esteira_model_cob/deploy_targets.py, exibido na nova seção DEPLOY do JCL Pipeline Report (python -m esteira_model_cob report jcl/poc001_sucesso.jcl --env TI).
  6. Repositório de artefatos: GitHub Artifacts/Releases. Confirmado (seção 1) como caminho inicial, sem JFrog Artifactory — implementar como parte do empacotamento (item ainda em aberto na Fase 1: não existe empacotamento hoje, só validação/simulação). Continua pendente — não há estágio de build/empacotamento nesta rodada (ver seção 6, item 1).
  7. Referenciar este documento a partir de integracao-zos.md, pre-requisitos-ambiente-real.md e validacao-tecnica.md (feito).

Médio prazo — depende de acesso real ao mainframe/L2

  1. Varredura hexadecimal no escopo real. Pedir/repetir, para os componentes que vão entrar no nosso escopo (JCL, e PROCs referenciadas), a mesma busca hexadecimal que a Ana fez na instância CWB — para não sermos surpreendidos por um componente já hex-declarado. Confirmado: nenhum componente real conhecido tem isso hoje (ver seção 5) — a varredura é preventiva, não corretiva.
  2. Teste de round-trip binário — em duas etapas, não uma só:
  3. 9a. Contra o "mainframe simulado" da nossa própria VM — não bloqueado, fazer já. O job publish do workflow (docs/ambiente-validacao.md) já promove artefatos validados para ~/publicado/<AMBIENTE>/... na VM self-hosted (equivalente atual a "mover o membro para a PDS do ambiente"). Hoje esse passo é um cp -r simples — não passa pelo codepage EBCDIC, então não reproduz a corrupção que a Ana descreveu, mas serve para provar que o resto da nossa própria esteira (git → binary_guard → .gitattributes → Python → publicação) preserva os bytes exatos da massa de teste do item 3, sem nenhuma reconversão UTF-8 acidental no caminho. Isso é validável agora, sem depender de credencial nenhuma do banco.
  4. 9b. Contra um z/OS real (Zowe/z/OSMF Files REST API). Só essa etapa depende do acesso/credenciais ao mainframe do banco (bloqueado, ver plano-inicial.md) — é a única forma de provar que o PUT /zosmf/restfiles/ds/... em modo binary realmente preserva o byte EBCDIC original num dataset de verdade, o que nenhuma simulação em VM Linux consegue reproduzir.
  5. Estrutura DBB/Zowe própria, sem depender da L2 corporativa. Ainda sem acesso ao que Diego/Eduardo/Gustavo têm validado na L2 (ver seção 5). Como a decisão é Zowe/z/OSMF direto (sem DBB), o que falta provisionar é Zowe CLI/SDK na VM de validação já existente (docs/ambiente-validacao.md) — não a estrutura DBB deles. Se a VM atual não tiver recurso/alcance de rede suficiente para o teste de conectividade real, sinalizar para provisionar mais recursos antes de travar nesse ponto.

6. Re-análise: diferenças da nossa POC em relação à esteira real (além do "mainframe" simulado em VM Linux)

Já é sabido e aceito que o nosso "mainframe" hoje é uma simulação: o MockZosAdapter gera JOBID/spool/RC em Python, e o job publish (docs/ambiente-validacao.md) "publica" o artefato validado com um cp -r para uma pasta comum de Linux (~/publicado/<AMBIENTE>/...) — sem JES, sem codepage EBCDIC, sem dataset de verdade. Essa é uma diferença já conhecida e endereçada no roadmap (Fase 2 = ZosmfAdapter real). A pergunta desta rodada foi: que outras diferenças existem, além dessa.
